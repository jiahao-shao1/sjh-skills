# research-lead

[English](README.md) | 中文

把一个研究问题推进到有证据的结论。默认由 **Opus 5.5 做 leader、Codex 做 executor**，执行者运行在用户能从 App 打开并继续对话的独立远程聊天中。模型可按用户要求调整；skill 本身不会切换当前会话的模型。

leader 负责理解背景、提出假设、设计最小实验、整理带来源和验收标准的任务，并审核关键证据。executor 核对实际代码和环境，实施、测试、运行已授权实验；发现方案与事实矛盾时回报，不机械执行。

## 安装与使用

```bash
npx skills add jiahao-shao1/sjh-skills --skill research-lead
npx skills add jiahao-shao1/sjh-skills --skill session-team
```

在 Opus 5.5 会话中说：

> 用 research-lead 推进这个问题：这次数据改动能否提升留出任务上的纠错能力？先读项目背景和已有证据。请组织一个我能在 App 里打开的 Codex 远程执行会话，并允许它向你回报。在已有预算内提出最小有价值的实验。

如果只想讨论方案，明确说“先只做设计”，不会因此创建团队。单次代码修复、状态查询或论文审读不需要这套流程。

## 职责边界

- **research-lead**：研究背景、假设、实验设计、证据审核和下一步决策。
- **session-team**：创建会话、通信、客户端可见性、工作区与资源归属、后续检查。自动协作需要安装它；缺少时仍可整理供手动使用的任务说明。
- **项目已有记录**：保存权威方案、实验状态和证据。[任务交接模板](references/handoff-template.md) 补充到已有记录中，不另建平行台账。

executor 完成后标记“待审核”；leader 分开判断实现完成和科学结论。用户直接给 executor 的新要求也要记录并同步。模型拒绝或 leader 中断，都不意味着可以扩大范围或自动把被拒任务转给另一模型继续。

## 验证状态

当前是一套工作约定，尚未证明能提升研究质量，也不保证避免模型拦截。先用一个真实、边界清楚的研究任务，观察背景遗漏、返工、用户协调次数和最终结论的证据质量。目标机器上的远程会话可见性与直接续聊能力，由 session-team 单独核验。
